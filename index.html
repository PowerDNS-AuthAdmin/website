Reverse DNS and Zone Monitoring

Two things PowerDNS cannot tell you from the inside: whether every address has the right PTR, and whether the rest of the internet can actually reach your zones. Both are opt-in.

Reverse DNS

PTR records that keep up with your A and AAAA records

Saving or deleting an A/AAAA record can create, update or remove its PTR in a reverse zone hosted on any backend, including RFC 2317 classless zones. The Reverse DNS report then compares every address in the fleet with its PTR and fixes what you pick.

  • Six statuses. OK, missing, mismatch, ambiguous, orphan and not hosted, ordered by count, with a sidebar badge for the addresses that need attention.
  • Rectify with a reviewed diff. One row, a selection or everything fixable. Removals and bulk fixes show the PTR diff for each reverse zone before Apply.
  • Suggested fixes for orphans. Add the missing forward record through the prefilled Add record wizard, or remove the PTR.
  • Public and internal kept apart. Public records only match public reverse zones and internal ones only internal. Addresses you don't host are looked up through your resolvers.
  • Never clobbers. Reverse zones are never created, and a PTR that points elsewhere is never replaced without an explicit takeover, and never deleted.

PTR on save is off until you enable the auto_ptr setting, a zone's X-AUTHADMIN-AUTO-PTR metadata, or tick the editor's PTR checkbox on a save. The report needs REVERSE_DNS_ENABLED=true.

Zone Monitoring

See your zones the way the internet does

A zone PowerDNS serves correctly can still be broken for everyone else: the wrong nameservers at the registrar, a DS left behind by a key rollover, a secondary that stopped transferring. AuthAdmin checks every hosted zone from the outside on a schedule.

  • Delegation from the root. The parent's NS set, glue and DS are read by walking down from the root servers, not through a recursive resolver.
  • Nameservers and open AXFR. Each nameserver is probed for reachability, the AA flag, its serial and NS set, and for an unsigned zone transfer.
  • DNSSEC chain and SOA. The DS at the parent against the zone's DNSKEYs, what resolvers answer, and SOA timers, MNAME and RNAME.
  • Fix with a reviewed diff. A wrong SOA MNAME gets a one-click Fix that shows the SOA before and after, saves it and re-checks the zone.
  • Findings in the bell. Errors and warnings reach the notification bell. A standalone backend can accept single-nameserver zones so they stay out of it.

Off unless ZONE_MONITOR_ENABLED=true: it sends DNS queries outside your network, bounded to three zones at a time with rate-limited re-checks.

Model Context Protocol

Talk to your DNS

A built-in MCP server lets Claude Code, Codex, Cursor or any MCP client manage zones and records from a prompt, and every new page has a tool too. The assistant never gets more power than the token you give it, and every change lands in the audit log.

  1. Create a token under Profile → API tokens and pick its scopes. zone.read alone for questions, add record.* for edits, or a single per-zone grant for a bot that should only ever touch one zone.
  2. Connect your client to /api/mcp over Streamable HTTP with the token as a Bearer header. Pick your client below.
  3. Ask. Task-shaped tools cover backends, zones and records, reverse DNS, Zone Monitoring, search and notifications. Writes go through the same validators, concurrency checks and NOTIFY as the UI.
# Claude Code: one command, then just ask
claude mcp add --transport http powerdns https://dns.example.com/api/mcp \
  --header "Authorization: Bearer pda_pat_xxxxxxxx"

# /mcp inside Claude Code shows the connection
{
  "mcpServers": {
    "powerdns": {
      "type": "http",
      "url": "https://dns.example.com/api/mcp",
      "headers": {
        "Authorization": "Bearer ${PDNS_AUTHADMIN_TOKEN}"
      }
    }
  }
}
# ~/.codex/config.toml
[mcp_servers.powerdns]
url = "https://dns.example.com/api/mcp"
bearer_token_env_var = "PDNS_AUTHADMIN_TOKEN"

# then: export PDNS_AUTHADMIN_TOKEN=pda_pat_xxxxxxxx
{
  "mcpServers": {
    "powerdns": {
      "url": "https://dns.example.com/api/mcp",
      "headers": {
        "Authorization": "Bearer pda_pat_xxxxxxxx"
      }
    }
  }
}
  • Runs as the token owner. Scopes and per-zone grants are the ceiling, re-evaluated on every call. Revoke the token and it stops.
  • Read-only token, read-only server. Write tools are only advertised to tokens that can write somewhere.
  • Audited by name. Each change records the owner and the client's user agent, so you can filter the log for what the assistant did.
  • Destructive calls flagged. Replace and delete tools are annotated so clients ask first; deleting a zone needs its name repeated.

Features

Everything you need to run authoritative DNS

Designed for teams that operate real, multi-backend PowerDNS infrastructure, from a homelab to a hosting provider.

PTR records that keep up

Saving or deleting an A/AAAA record can create, update or remove its PTR in a reverse zone on any backend, and a fleet-wide Reverse DNS report shows every address that is missing, mismatched or orphaned.

Zone Monitoring

Every hosted zone checked from the outside: delegation walked from the root servers, each nameserver, open AXFR, the DNSSEC chain and what resolvers answer. Findings feed the notification bell.

Talk to your DNS

A built-in MCP server lets Claude Code, Codex, Cursor or any MCP client manage zones and records, reverse DNS and monitoring from a prompt, under the same RBAC, validation and audit log as the UI.

Real RBAC

Five system roles plus your own custom roles across ~60 permissions, each assignment scoped to global, team, zone or server.

SSO your way

OIDC with PKCE, SAML 2.0 and LDAP / Active Directory, all with group → role mapping. Local accounts use Argon2id.

Passkeys & MFA

Passkeys and hardware security keys (WebAuthn) or TOTP. Any role can require MFA before it takes effect.

Diff before apply

Edit records inline, in the full editor or through the Add record wizard, drive it all from the keyboard, and review every change as a BIND-style diff before it is written.

Multi-backend, in sync

Standalone primaries, primary + secondaries and multi-primary clusters in one zone list, with NOTIFY-aware probes that compare every secondary's serial.

DNSSEC & TSIG

Enable, disable and rectify DNSSEC per zone, publish the right DS set, manage cryptokeys, TSIG keys and autoprimaries without pdnsutil.

Append-only audit

Every write, including what an AI assistant does, is recorded with redacted before / after snapshots and the PowerDNS HTTP trail, with a fleet-wide Change log and one per zone.

One image, zero clicks

A single Docker image on SQLite or Postgres. A provisioning.yaml brings up roles, teams, backends and SSO on first boot.

Search everything

Ctrl K / ⌘K fuzzy-matches zones, records and config across every backend, filtered by your own permissions. The request and audit logs have their own tabs.

Quickstart

Self-host it with Docker Compose

One image, ghcr.io/powerdns-authadmin/powerdns-authadmin. Runs on SQLite or Postgres, and migrations plus the role seed run automatically on boot.

mkdir powerdns-authadmin && cd powerdns-authadmin

# 1. Generate secrets once. Back this file up and never change them.
{
  echo "APP_SECRET_KEY=$(openssl rand -base64 32)"
  echo "APP_ENCRYPTION_KEY=$(openssl rand -base64 32)"
  echo "BOOTSTRAP_ADMIN_EMAIL=admin@example.com"
  echo "BOOTSTRAP_ADMIN_PASSWORD=$(openssl rand -base64 18)"
  echo "APP_URL=https://dns.example.com"   # the exact URL your browser uses
} > .env
chmod 600 .env

# 2. Save compose.yml (next tab), then start it
docker compose up -d
# compose.yml: single instance on SQLite
services:
  app:
    image: ghcr.io/powerdns-authadmin/powerdns-authadmin:latest
    restart: unless-stopped
    ports: ["3000:3000"]
    environment:
      APP_URL: ${APP_URL}
      DATABASE_URL: file:/data/powerdns_authadmin.db
      APP_SECRET_KEY: ${APP_SECRET_KEY}
      APP_ENCRYPTION_KEY: ${APP_ENCRYPTION_KEY}
      BOOTSTRAP_ADMIN_EMAIL: ${BOOTSTRAP_ADMIN_EMAIL}
      BOOTSTRAP_ADMIN_PASSWORD: ${BOOTSTRAP_ADMIN_PASSWORD}
      # Optional: apply provisioning.yaml once on first boot
      # PROVISION_ON_BOOT: "true"
      # PROVISIONING_FILE: /etc/pda/provisioning.yaml
    volumes:
      - app-data:/data
      # - ./provisioning.yaml:/etc/pda/provisioning.yaml:ro
volumes:
  app-data:
# provisioning.yaml: applied once on first boot, then the UI
# is the source of truth. Every block is optional.
settings:
  site_name: "ACME DNS"
  default_record_ttl: 300

# Register your PowerDNS Authoritative backend(s)
pdns_servers:
  - slug: primary
    name: "Primary PowerDNS"
    base_url: "https://pdns.internal:8081/api/v1"
    server_id: localhost
    api_key: "change-me-pdns-api-key"   # encrypted at rest
    is_default: true
  1. Generate secrets once into a persistent .env. A regenerated APP_ENCRYPTION_KEY makes stored API keys and MFA secrets unreadable, so back it up.
  2. Set APP_URL to the exact URL your browser uses, scheme and host included.
  3. Start it with docker compose up -d and sign in with the bootstrap admin.
  4. Optional: add a provisioning.yaml to register backends, roles, teams and SSO on first boot.

FAQ

Common questions

What is PowerDNS-AuthAdmin?

PowerDNS-AuthAdmin is a free, open-source web interface for managing PowerDNS Authoritative servers. It adds role-based access control, single sign-on (OIDC, SAML and LDAP), passkeys and MFA, a diff-before-apply record editor, automatic PTR maintenance with a fleet-wide Reverse DNS report, Zone Monitoring of delegation, nameservers and DNSSEC from the outside, DNSSEC and TSIG management, multi-backend cluster support, an append-only audit log and a built-in MCP server for AI assistants on top of the PowerDNS HTTP API. It ships as one Docker image and is MIT licensed.

Can PowerDNS-AuthAdmin keep PTR records in sync?

Yes, since version 1.10.0. With automatic PTR maintenance on, saving or deleting an A or AAAA record also creates, updates or removes the matching PTR in a reverse zone hosted on any of your backends, including RFC 2317 classless zones, and the review dialog shows the reverse change before you save. Turn it on globally with the auto_ptr setting, per zone with X-AUTHADMIN-AUTO-PTR metadata, or for one save with the editor's checkbox; nothing is written otherwise. It never creates reverse zones and never replaces a PTR that points at another name without an explicit takeover. To reconcile what is already there, set REVERSE_DNS_ENABLED=true for the Reverse DNS report, which compares every A/AAAA record in the fleet with its PTR (OK, missing, mismatch, ambiguous, orphan, not hosted) and rectifies the rows you pick after showing the PTR diff. See the feature reference.

Does it monitor delegation, nameservers and DNSSEC?

Yes, since version 1.10.0, when you set ZONE_MONITOR_ENABLED=true. Zone Monitoring checks every hosted zone from the outside on a schedule: the delegation at the parent, read by walking from the root servers rather than through a resolver, each nameserver's reachability, authority, serial and NS set, open AXFR, the DS at the parent against the zone's DNSKEYs, what public or internal resolvers answer, and the SOA timers, MNAME and RNAME. Findings have stable codes, a severity and what to do; errors and warnings appear in the notification bell, and an SOA MNAME finding has a Fix button that shows the change as a diff before saving. It is off by default because it sends DNS queries outside your network. See the feature reference and the configuration guide.

Which PowerDNS versions does it support?

PowerDNS-AuthAdmin is tested in CI against PowerDNS Authoritative 4.6 to 5.1 (4.6, 4.7, 4.8, 4.9, 5.0 and 5.1). It talks to PowerDNS through the Authoritative server's built-in HTTP API, so the API and an API key must be enabled. Catalog zones need PowerDNS 4.7 or later, and on 5.1 editing LUA records needs enable-lua-record-updates=yes.

Can I manage DNS with Claude Code or another AI assistant?

Yes. Since version 1.9.0, PowerDNS-AuthAdmin includes a Model Context Protocol (MCP) server at /api/mcp. Connect Claude Code, Codex, Cursor, Windsurf or any MCP client over Streamable HTTP with a personal access token as the Bearer header, then ask in plain language: point www at an address, replace a zone's MX records, create a staging zone. The assistant gets tools for backends, zones and records, and since 1.10.0 for everything the new pages do: finding a zone, checking a name before adding it, waiting for a zone to sync, the Reverse DNS report and its rectify, Zone Monitoring, search and notifications. See the MCP guide for each client's configuration.

Yes. PowerDNS-AuthAdmin is free and community supported: ask questions in GitHub Discussions and report bugs in Issues. Commercial support, 24 hours a day, is available from Next Generation Networks (NGN), the Sydney IT company that built this website; see commercial support for how to reach them.
